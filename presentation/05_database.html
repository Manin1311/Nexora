Key Database Design Decisions

✅ Why JSONField for Resume Data?

Resume sections (experience, projects, skills) have variable structure. Instead of 6+ additional tables with complex joins, we store them as JSON in PostgreSQL's native JSONField. This allows: nested arrays of bullets, flexible field names, and fast single-query fetch. Trade-off: cannot run SQL queries ON resume fields (e.g., SELECT * WHERE resume.skills CONTAINS "Python") — but we never need to.

🔐 Why UUID for AssessmentSession?

OA simulation sessions use UUIDField as primary key instead of auto-increment. This prevents ID enumeration attacks (guessing other users' session IDs by incrementing). With UUID4, there are 2^122 possible values — practically impossible to guess.

✅ Why OneToOne for Profile/Resume/AIMemory?

User has EXACTLY ONE profile, one resume, one AI memory — a strict 1:1 relationship. OneToOneField creates a unique database constraint ensuring duplicates are impossible. Also makes access clean: user.profile, user.resume, user.ai_memory — no queryset needed.

🔗 unique_together on ChallengeSubmission

Meta: unique_together = ('user', 'challenge') — enforced at the database level. Prevents a user from having two submissions for the same challenge. The view uses get_or_create(user, challenge) which safely updates if exists. Without this DB constraint, race conditions could create duplicates.
